# DGS

Тестовый магазин цифровых товаров. В проекте есть витрина по макету, оформление заказа, имитация оплаты, автоматическая выдача ключа и восстановление неудачных доставок.

Серверная часть и интерфейс работают в одном Symfony-приложении. Страницы собраны на Twig, интерактивность написана на обычном JavaScript, а фоновые задачи обрабатываются через Symfony Messenger.

## Что реализовано

- Адаптивная витрина с каталогом, каруселью, поиском, избранным и карточками товаров.
- Форма пополнения Steam с переключателем `$/₸/₽` внутри поля суммы. Переключатель меняет активную валюту без пересчёта цены.
- Создание и просмотр заказа через API.
- Приём уведомлений об успешной и неуспешной оплате.
- Асинхронная обработка платежей и автоматическая выдача ключа.
- Два тестовых поставщика — A и B — с настраиваемыми ошибками и таймаутами.
- Повторная доставка после пополнения пустого пула ключей.
- Промокоды с ограничением количества использований.
- Защита от повторного создания заказа, дубликатов уведомлений и двойной выдачи ключа.

## Стек

- PHP 8.4 и Symfony 8.1
- Doctrine ORM и DBAL
- PostgreSQL 17
- Twig и AssetMapper
- Symfony Messenger
- FrankenPHP
- Docker Compose

Node.js для запуска и сборки проекта не требуется.

## Запуск

Нужны Docker и Docker Compose v2.

```bash
docker compose up -d --build
```

После запуска витрина доступна по адресу <http://localhost:8080>.

При первом старте автоматически устанавливаются зависимости, выполняются миграции и добавляются демонстрационные товары, промокоды и ключи. Отдельные контейнеры запускают приложение, обработчик фоновых задач и PostgreSQL.

Остановить проект:

```bash
docker compose down
```

## Проверка

Все тесты и проверки запускаются одной командой:

```bash
make acceptance
```

Команда запускает PHPUnit, PHPStan, CS Fixer, проверку схемы Doctrine, Twig и DI-контейнера, а затем проверяет конкурентные запросы через HTTP.

Отдельные команды:

```bash
make test       # интеграционные тесты на отдельной тестовой базе
make quality    # статический анализ и проверки конфигурации
make race       # сценарии с параллельными заказами и уведомлениями
make logs       # логи приложения и обработчика фоновых задач
```

`scripts/race-test.sh` воспроизводит:

- 50 одновременных запросов на создание одного заказа;
- 50 одинаковых уведомлений об оплате;
- 50 разных событий оплаты одного заказа;
- уведомление, полученное до создания заказа;
- 10 одновременных заказов с промокодом, рассчитанным на 3 использования.

После выполнения скрипт проверяет количество заказов, событий, обращений к поставщику, выданных ключей и использований промокода непосредственно в PostgreSQL.

## API

### Создать заказ

```bash
curl -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"sku":"KEY-CS2-PRIME","client_request_id":"0199a9f0-509f-7d83-93de-d1b1acf12e78","promo_code":"WELCOME10"}'
```

`client_request_id` используется как ключ идемпотентности. Повторный запрос с тем же значением вернёт уже созданный заказ.

Получить состояние заказа:

```text
GET /api/orders/{id}
```

Возможные статусы:

```text
created → paid → delivering → delivered
               ↘ out_of_stock
               ↘ delivery_failed
created → payment_failed
```

### Отправить уведомление об оплате

```bash
curl -X POST http://localhost:8080/api/webhooks/payment \
  -H 'Content-Type: application/json' \
  -d '{"event_id":"evt-1","order_id":"<uuid>","status":"paid","amount":1161,"currency":"RUB","created_at":"2026-08-31T12:00:00+03:00"}'
```

Запрос быстро сохраняется и возвращает `200`. Дальнейшая обработка выполняется в фоне. Повторное событие с тем же `event_id` принимается без повторной выдачи товара. Если событие пришло раньше заказа, оно будет обработано после его появления.

### Проверить тестового поставщика

```bash
curl -X POST http://localhost:8080/api/suppliers/A/issue \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"stable-request-1","sku":"KEY-CS2-PRIME","order_id":"<uuid>","mode":"timeout"}'
```

Параметр `mode` принимает значения `timeout` и `error`. Вероятности случайных ошибок и таймаутов задаются переменными окружения:

```text
SUPPLIER_A_FAILURE_RATE
SUPPLIER_A_TIMEOUT_RATE
SUPPLIER_B_FAILURE_RATE
SUPPLIER_B_TIMEOUT_RATE
SUPPLIER_TIMEOUT_SECONDS
```

Одинаковый `request_id` всегда возвращает результат одной и той же операции. Это позволяет безопасно повторить запрос после таймаута.

## Администрирование

Административные API-методы требуют заголовок:

```text
X-Admin-Token: dev-admin-token
```

Доступные методы:

```text
GET  /api/admin/orders
POST /api/admin/inventory
POST /api/admin/orders/{id}/retry
```

`GET /api/admin/orders` возвращает только заказы, которым требуется вмешательство: `out_of_stock` и `delivery_failed`. После добавления ключей доставку можно повторить — повторный вызов не выдаст второй ключ.

Страница со списком проблемных заказов доступна по адресу <http://localhost:8080/admin>.

## Как предотвращается двойная выдача ключа

Повторные запросы отсекаются уникальными идентификаторами заказа, события оплаты и обращения к поставщику. Во время доставки заказ блокируется, а свободный ключ резервируется через `FOR UPDATE SKIP LOCKED`. Ограничения PostgreSQL дополнительно запрещают назначить заказу второй ключ.

Операции, которым нужны `ON CONFLICT`, блокировка строк или advisory lock, находятся в репозиториях. Остальные чтения и изменения выполняются через Doctrine ORM; SQL в контроллерах и прикладных сервисах отсутствует.

Основные сущности: `Product`, `PurchaseOrder`, `PaymentEvent`, `PromoCode`, `PromoRedemption`, `InventoryKey`, `SupplierIssue` и `DeliveryAttempt`.
